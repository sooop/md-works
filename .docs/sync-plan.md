# 기기 간 동기화 구현 계획 (Cloudflare Worker + D1)

## 요약

스탠드얼론 HTML 버전의 글·글감·스레드를 여러 기기에서 동기화한다. 서버는 Cloudflare 무료 플랜의 Worker 1개와 D1 1개다. 같은 동기화 키를 입력한 기기끼리 데이터를 공유하고, 데이터는 브라우저에서 암호화한 항목 단위로만 서버에 둔다. 서버는 복호화하지 않는다.

기본 설계는 첨부 문서 「독립실행 HTML 앱용 Cloudflare Worker 동기화 구현」을 따른다. 이 문서는 문서에서 바뀐 부분과 md-works 에 맞춘 부분만 적는다. API 형식, D1 스키마 골격, 키 파생, 암호화 형식은 첨부 문서 그대로다.

## 범위

포함:
- 스탠드얼론 HTML 의 글, 글감, 스레드 동기화와 삭제 전파
- Worker + D1 서버, 클라이언트 동기화 모듈, 동기화 대화상자
- 배포 안내 README

제외:
- 서버 버전(노트 폴더). 기존 번들·폴더 백업을 그대로 쓴다.
- 이력(`versions`). 기기마다 로컬에 둔다.
- 이미지. 본문만 동기화하고, 이미지가 없는 기기에는 안내를 보인다.
- 실시간 푸시, 계정 로그인, 키 복구.

## 확정 결정

| 주제 | 결정 |
|---|---|
| 동기화 항목 | 글(`doc`), 글감(`snippet`), 스레드(`thread`). 글 삭제는 서버의 삭제 표시(`deleted`)로 전파한다. 별도 묘비 항목은 없다 |
| 항목 id | 글 `d` + `contentHash(이름.toLowerCase())`, 글감 `s-` + 글감 id, 스레드 `t-` + 스레드 id. 62자를 넘는 id 는 `contentHash` 로 줄인다 |
| 서버에 이름을 숨긴다 | 글 이름은 암호화된 평문 안에만 둔다. 서버는 해시 id 만 안다 |
| 압축 | 평문 JSON 을 deflate(`fflate`, 이력 압축과 같은 방식) 한 뒤 AES-GCM 으로 암호화한다. 전송 형식은 base64(IV ‖ 암호문 ‖ 태그) |
| 충돌 | `updatedAt` 이 큰 쪽이 이긴다. 진 쪽이 글이면 로컬 이력에 '동기화 전' 버전으로 남긴다. 서버에는 올리지 않는다 |
| 이미지 | 글 본문의 `idb:` 참조는 그대로 동기화한다. 이미지가 없는 기기는 깨진 이미지 자리에 번들 이동 안내를 보인다 |
| 삭제와 오래된 기기 | 보관 기간(`TOMBSTONE_DAYS`) 안에는 자동 전파한다. 커서가 서버의 `purged_seq` 보다 작은 기기는 `resyncRequired` 를 받고, 서버에 없는 로컬 항목을 올릴지 지울지 사용자에게 묻는다 |
| 키 | 앱이 만든 무작위 키만 허용한다(HKDF) |
| UI | 별도 '동기화' 대화상자. 키·Worker 주소·초대 코드는 번들·내보내기에 넣지 않는다 |
| Worker 주소 | `workers.dev` |
| 설정 방식 | Wrangler CLI |

## 첨부 문서에서 바뀐 값

| 변수 | 첨부 문서 | 이 계획 | 이유 |
|---|---|---|---|
| `MAX_ITEM_BYTES` | 65536 | 262144 | 압축하지만 긴 글이 많다. blob 문자열 길이 기준 |
| `MAX_SPACE_BYTES` | 3145728 | 5242880 | 글 약 100편(압축 후 평균 약 40 KB)을 담는다 |
| `MAX_SPACES` | 100 | 60 | 최악 합계 300 MB 로 D1 무료 DB 500 MB 이내 |
| `MAX_ITEMS_PER_SPACE` | 1000 | 1000 | 변경 없음 |
| `MAX_DAILY_WRITES` | 300 | 300 | 변경 없음. 배포 후 실측해 조정 |
| `TOMBSTONE_DAYS` | 30 | 30 | 변경 없음 |

스키마 변경: `spaces` 에 `purged_seq INTEGER NOT NULL DEFAULT 0` 을 추가한다. 보관 기간이 지나 정리한 삭제 항목 중 가장 큰 `seq` 를 기록한다.

API 변경: 요청의 `cursor` 가 0 보다 크고 `purged_seq` 보다 작으면 응답에 `resyncRequired: true` 를 넣고, 서버는 `cursor` 를 0 으로 보고 변경분을 돌려준다. 요청 `push` 는 이 경우 무시한다(클라이언트가 처리 방식을 정한 뒤 다시 보낸다).

## md-works 에 맞춘 부분

- **로컬 id 가 기기마다 다르다.** 스탠드얼론에서 글의 로컬 id(docKey)는 기기마다 다르다. 스레드의 `docKey` 와 글감의 `attachedDocs`, `orders` 는 동기화 평문에서 글 이름(소문자)으로 바꿔 보내고, 받는 쪽 어댑터가 그 기기의 docKey 로 다시 바꾼다. 해당 글이 아직 없으면 그 글을 받은 뒤 다시 적용한다(보류).
- **글 이름 변경.** 옛 이름 삭제와 새 이름 생성으로 전파한다. 이력·스레드는 새 이름으로 따라간다(로컬 동작은 기존과 같다).
- **변경 감지.** 엔진은 항목별 `contentHash` 를 메타에 두고 로컬 목록과 비교해 dirty 를 판정한다. 로컬 저장소 코드는 고치지 않는다.
- **대량 삭제 가드.** 로컬 목록에서 항목이 한꺼번에 사라진 것처럼 보이면(항목 6개 이상이고 절반 이상) 푸시를 멈추고 사용자에게 확인한다. 저장소를 못 읽은 경우에 서버가 비워지는 사고를 막는다.
- **쓰기량 줄이기.** 편집 5초 디바운스에 더해, 같은 항목은 30초에 한 번까지만 푸시한다. 일일 쓰기 한도의 80% 에 가까워지면 푸시 간격을 5분으로 늘리고 대화상자에 표시한다.
- **로컬 메타.** IndexedDB `works-sync`(`meta`: id → rev, hash, updatedAt, deleted / `state`: 커서, 마지막 동기화 시각)에 둔다. 번들에 넣지 않는다.

## 파일 구성과 담당

```
sync-worker/                  (담당 A) Worker 프로젝트
  wrangler.toml  schema.sql  package.json  tsconfig.json
  src/index.ts  src/handler.ts  src/limits.ts
  test/                       node:sqlite 로 만든 D1 호환 모의 + vitest
  README.md                   (담당 F, 배포 안내)
src/lib/sync/
  protocol.ts                 (공용 계약, 이미 작성됨 — 수정 금지)
  keys.ts  codec.ts           (담당 B) 키 생성·파생, 암호화·압축
  transport.ts  engine.ts     (담당 C) 요청·재시도·커서·충돌 판정·스케줄
  adapter.ts                  (담당 D) 로컬 저장소 ↔ 동기화 항목
  state.svelte.ts             (담당 E) 반응형 상태·설정 저장
src/lib/components/SyncDialog.svelte   (담당 E)
tests/sync/                   각 담당이 자기 파일의 테스트를 둔다
```

담당끼리 파일이 겹치지 않는다. 의존은 `protocol.ts` 의 인터페이스로만 한다. 통합(배선: `StandaloneShell`, 명령 팔레트, 쓰기 감지 연결)은 모든 담당이 끝난 뒤 메인이 한다.

## 인수 기준

서버(`sync-worker/test`):
1. 초대 코드 없이 새 공간을 만들면 403, 있으면 만들어진다.
2. 잘못된 토큰은 401 이다.
3. `appId` 나 키가 다른 공간은 서로 읽을 수 없다.
4. 항목 크기·항목 수·공간 용량·일일 쓰기 한도를 넘으면 각각 413/422/429 로 거부한다.
5. 같은 `baseRev` 로 두 번 보내면 한쪽만 수락하고 다른 쪽은 `conflicts` 를 받는다.
6. 변경이 없는 요청은 D1 에 쓰지 않는다.
7. D1 덤프에 평문이 없다(blob 은 불투명 문자열).
8. 삭제가 전파되고, 보관 기간이 지난 삭제 항목은 정리되며 `purged_seq` 가 올라간다. 오래된 커서는 `resyncRequired` 를 받는다.

클라이언트(`tests/sync`):
1. 키 파생이 첨부 문서의 규칙과 같다(고정 입력 → 고정 출력).
2. 암호화 왕복이 되고, 항목 id 가 다르면 복호화에 실패한다(AAD).
3. 오프라인에서 편집한 항목이 재접속 후 올라간다.
4. 두 기기가 같은 글을 따로 고친 뒤 접속하면 한 값으로 수렴하고, 진 글은 이력에 남는다.
5. 401·429·503·413 에서 각각 정해진 동작을 한다.
6. 글 이름이 기기마다 다른 docKey 로 매핑되어 스레드·글감 연결이 유지된다.
7. 대량 삭제 가드와 `resyncRequired` 흐름이 동작한다.
8. `npm run check`, `npm test` 가 통과한다.

## 남은 위험

- 쓰기 행 3개/건은 문서의 추정이다. 배포 후 D1 대시보드로 실측한다.
- 글 본문이 `MAX_ITEM_BYTES` 를 넘으면 그 글만 동기화되지 않는다. 대화상자에 목록을 보인다.
- 스레드의 글 매핑은 이름 기준이라 한쪽에서 이름을 바꾸면 다른 기기에서 일시적으로 끊길 수 있다.
