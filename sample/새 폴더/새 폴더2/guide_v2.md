# 1. 들어가며

Word 문서를 프로그램으로 만들어야 할 때 선택지는 생각보다 많고, 어떤 방식을 고르느냐에 따라 작성량, 수정 비용, 결과물의 완성도가 크게 달라집니다. 이 문서는 그중 실무에서 가장 자주 만나는 세 가지, 곧 docx-js로 코드를 짜는 방식, 마크다운을 pandoc으로 변환하는 방식, 그리고 둘을 섞은 하이브리드 방식을 비교합니다. 읽고 나면 만들려는 문서의 성격에 따라 어떤 방식을 골라야 하는지, 그리고 골랐을 때 어디서 막히기 쉬운지를 스스로 판단할 수 있게 됩니다.

비교의 근거는 두 가지입니다. 하나는 같은 보고서를 세 방식으로 직접 만들어 소스 크기, 토큰 수, 변환 시간을 측정한 실험이고, 다른 하나는 각 도구의 일반적인 특성입니다. 두 근거는 구분해서 쓰며, 실험으로 확인하지 못한 부분은 8장에 따로 모아 두었습니다.

먼저 결론을 말하면, 본문 중심의 문서를 반복해서 만든다면 하이브리드 방식이 가장 효율적이고, 레이아웃을 정밀하게 제어해야 하거나 데이터로 문서를 대량 생성해야 할 때만 docx-js로 가는 것이 좋습니다. 이유는 다음 장에서 docx 파일의 구조를 이해하면 자연스럽게 드러납니다.

> **한 줄 요약.** 내용은 마크다운으로, 서식은 템플릿으로 분리하면 작성량과 수정 비용이 가장 줄어듭니다. 이 분리가 어울리지 않는 문서에서만 docx-js를 선택하세요.

| 항목 | docx-js | 마크다운 + pandoc | 하이브리드 |
|:---|:---|:---|:---|
| 소스 작성량 | 많음 | 적음 | 적음 |
| 서식 정밀도 | 높음 | 낮음 | 템플릿이 정의한 범위 안에서 높음 |
| 본문 수정 | 코드 수정 | 텍스트 수정 | 텍스트 수정 |
| 초기 준비 | 없음 | 없음 | 템플릿 제작 |
| 어울리는 문서 | 정밀 레이아웃, 자동 생성 | 단순하고 일회성 | 반복 생성, 조직 양식 |

# 2. docx 파일을 이해하면 선택이 쉬워집니다

세 방식은 겉보기에는 전혀 다른 도구지만, 사실 하나의 질문에 서로 다르게 답하는 것입니다. 그 질문은 “문서의 내용과 서식을 누가, 어디서 결정하는가”입니다. 이 질문이 왜 중요한지는 docx 파일이 어떻게 생겼는지 보면 알 수 있습니다.

docx는 XML 파일 여러 개를 ZIP으로 묶은 것입니다. 본문 문단은 `word/document.xml`에, 제목이나 본문 같은 스타일의 정의는 `word/styles.xml`에 따로 들어 있습니다. 본문의 문단은 “이 문단은 Heading 1 스타일이다”라고만 말하고, Heading 1이 어떤 글꼴과 크기와 색인지는 스타일 정의가 말합니다. 즉 docx는 애초에 내용과 서식이 분리된 구조입니다. Word에서 스타일을 바꾸면 문서 전체의 제목 모양이 한꺼번에 바뀌는 것도 이 때문입니다.

이 관점에서 보면 세 방식의 차이가 선명해집니다. docx-js는 문단마다 서식을 코드로 선언하므로 내용과 서식을 한 곳에서 함께 결정합니다. 마크다운 + pandoc은 내용만 쓰고 서식은 pandoc이 가진 기본 스타일에 맡깁니다. 하이브리드는 서식의 결정권을 우리가 만든 템플릿의 스타일 정의로 옮깁니다. 하이브리드가 효율적인 이유는 docx가 원래 가진 분리 구조를 그대로 활용하기 때문이며, 뒤에서 다룰 실측 결과도 이 구조에서 나옵니다.

# 3. 세 가지 방식의 작동 원리와 장단점

## 3.1 docx-js

docx-js는 npm 패키지 `docx`로, 문서의 구조를 JavaScript 객체로 선언해 파일을 만듭니다. 문단, 텍스트 런, 표, 셀, 번호 매기기 설정을 모두 명시적으로 적어야 하고, 그 대신 docx 명세가 허용하는 거의 모든 것을 제어할 수 있습니다.

    new Paragraph({
      heading: HeadingLevel.HEADING_2,
      children: [new TextRun("1. 주요 성과")],
    })

이 방식의 강점은 통제력입니다. 페이지 크기와 여백, 머리글과 바닥글, 셀 병합과 개별 셀의 음영, 이미지와 각주까지 코드 한 곳에서 정하고, 결과가 코드로 결정되므로 같은 입력에는 같은 문서가 나옵니다. 데이터를 읽어 반복문으로 문서 수백 개를 찍어 내는 자동화에도 자연스럽게 맞습니다.

반면 그 통제력의 값은 장황함으로 치릅니다. 이번 실험에서 같은 보고서가 마크다운으로는 393자였는데 docx-js 스크립트로는 3,679자였습니다. 본문을 고칠 때도 텍스트가 아니라 코드를 고쳐야 하고, 이미 있는 docx 파일을 열어 수정할 수는 없어 새 문서만 만들 수 있습니다. 표 스타일처럼 API가 없는 요소는 XML을 직접 끼워 넣어야 하는 경우도 있는데, 이는 7장에서 다시 다룹니다.

## 3.2 마크다운 + pandoc

마크다운 + pandoc은 반대쪽 극단입니다. 본문을 마크다운으로 쓰고 명령어 한 줄로 변환합니다.

    pandoc report.md -o report.docx

제목은 `#`, 목록은 `-`, 표는 파이프, 강조는 `**`로 쓰므로 작성량이 가장 적고, 텍스트 파일이라 수정과 버전 비교가 쉽습니다. 같은 소스를 HTML이나 PDF로도 변환할 수 있다는 점도 다른 두 방식에는 없는 장점입니다.

문제는 서식이 pandoc 기본 스타일에 고정된다는 것입니다. 이번 실험의 기본 변환 결과에서 표는 상단 구분선만 있었고 숫자도 왼쪽으로 정렬되어, 같은 내용을 docx-js로 만든 문서(전체 테두리, 음영이 들어간 헤더, 오른쪽 정렬 숫자)와 인상이 달랐습니다. 쪽 번호나 머리글도 마크다운 본문에서는 지정할 수 없습니다. 서식 요구가 낮은 문서에는 충분하지만, 조직의 양식을 지켜야 하는 문서에는 부족합니다.

## 3.3 하이브리드: 템플릿 + 마크다운 + pandoc

하이브리드는 두 방식의 약점을 서로 메웁니다. 마크다운 본문은 그대로 쓰되, pandoc의 `--reference-doc` 옵션으로 스타일이 정의된 템플릿 docx를 지정합니다. pandoc은 이 파일의 본문은 버리고 스타일 정의, 페이지 설정, 머리글과 바닥글만 가져다 쓰기 때문에, 서식은 템플릿이 정하고 내용은 마크다운이 정하는 분업이 됩니다.

    pandoc report.md --columns=30 --reference-doc=template.docx -o report.docx

템플릿은 Word에서 스타일을 편집해 만들어도 되고, 이번 실험처럼 docx-js로 만들어도 됩니다. 어느 쪽이든 한 번만 만들어 두면 이후 모든 문서에 재사용됩니다. 서식 정밀도는 템플릿이 정의한 스타일 범위 안에서 결정되므로, 이번 실험에서는 docx-js로 직접 만든 문서와 거의 같은 모양이 나왔습니다.

단점은 세 가지입니다. 템플릿을 만드는 초기 비용이 있고, 템플릿이 정의하지 않은 서식(예: 임의 셀 병합)은 여전히 어렵고, 템플릿 파일을 따로 보관하고 관리해야 합니다. 초기 비용은 다음 장의 수치로 얼마나 빨리 회수되는지 확인할 수 있습니다.

# 4. 실측 비교

같은 내용의 보고서를 세 방식으로 만들어 비교했습니다. 문서는 제목, 강조가 들어간 문단, 글머리 목록, 3열 표, 번호 목록으로 이루어진 25줄 분량입니다. 토큰 수는 OpenAI의 o200k_base 토크나이저로 센 근사치이고, 변환 시간은 프로세스 시작 시간을 포함해 10회 측정한 평균입니다.

| 방식                          | 소스 파일        | 줄 수 |  토큰 | 변환 시간 |
|:------------------------------|:-----------------|------:|------:|----------:|
| docx-js (문서 전체)           | report.js        |   137 | 1,042 |     118ms |
| 마크다운 + pandoc (기본)      | report.md        |    25 |   229 |      43ms |
| 하이브리드 (문서 소스)        | report_tpl.md    |    25 |   231 |      30ms |
| 하이브리드 (템플릿, 최초 1회) | make_template.js |   109 | 1,445 |     120ms |

이 표에서 읽어야 할 것은 두 가지입니다. 첫째, 문서 한 건당 하이브리드의 소스는 docx-js의 약 4.5분의 1이라 문서마다 약 810토큰이 절약됩니다. 템플릿을 만드는 데 든 1,445토큰은 문서 두 건째에서 회수됩니다. 한 건까지는 1,676 대 1,042로 오히려 손해이고, 두 건에서 1,907 대 2,084로 역전됩니다. 둘째, 변환 시간은 세 방식 모두 0.2초 안에 끝나므로 실질적인 판단 기준이 되지 못합니다. 속도보다 중요한 것은 소스를 쓰고 고치는 비용입니다.

결과물의 모양도 확인했습니다. 하이브리드 결과는 docx-js로 직접 만든 문서와 표 테두리, 헤더 음영, 숫자 정렬, 제목 색상이 거의 같았습니다. 다만 표의 열 너비 비율이 46 대 27 대 27로, docx-js 쪽의 44 대 28 대 28과 조금 달랐습니다.

> **측정의 한계.** 문서 한 건, 25줄이라는 아주 작은 표본이고 토큰 수도 근사치입니다. 문서가 길어지면 docx-js의 고정 비용(표와 목록 설정)의 비중은 줄지만, 문단마다 붙는 래퍼 코드 때문에 마크다운이 유리하다는 방향은 유지될 것으로 보입니다. 다만 긴 문서로는 측정하지 않았습니다.

# 5. 기능별 비교

수치 비교만으로는 “그 방식으로 이 기능이 되는가”를 알 수 없으므로 기능 단위로도 정리했습니다. 이 표에서 이번 세션에 직접 확인한 것은 제목, 목록, 표, 강조, 템플릿을 통한 표 스타일, 페이지 설정, 쪽 번호이고, 나머지는 각 도구의 일반적인 지원 범위입니다.

| 기능 | docx-js | 마크다운 + pandoc | 하이브리드 |
|:---|:---|:---|:---|
| 제목, 문단, 목록, 강조 | 가능 | 가능 | 가능 |
| 표 (테두리, 헤더 음영) | 가능 | 기본 서식만 | 템플릿의 표 스타일로 가능 |
| 셀 병합, 개별 셀 서식 | 가능 | 제한적 | 제한적 |
| 머리글, 바닥글, 쪽 번호 | 가능 | 지정 불가 | 템플릿에 정의하면 가능 |
| 목차 | 가능 | 가능 (열 때 갱신 필요) | 가능 (열 때 갱신 필요) |
| 각주, 이미지, 수식 | 가능 | 가능 | 가능 |
| 섹션별 다른 페이지 설정 | 가능 | 제한적 | 제한적 |
| 변경 추적, 주석 만들기 | 가능 | 제한적 | 제한적 |
| 기존 docx 파일 수정 | 불가 | 불가 | 불가 |
| PDF, HTML 등 다른 형식으로 재사용 | 불가 | 가능 | 가능 |

기존 파일 수정이 세 방식 모두 불가로 나오는 점에 주목하세요. 이 세 방식은 모두 문서를 새로 만드는 도구이고, 이미 있는 docx를 고치려면 압축을 풀어 XML을 직접 편집하는 별도의 접근이 필요합니다. 이 표가 다음 장의 선택 기준으로 이어집니다.

# 6. 어떤 경우에 어떤 방식을 고를까

선택 기준은 문서의 성격에서 나옵니다. 아래 표는 흔한 상황을 방식에 대응시킨 것이고, 각 행의 이유가 중요합니다.

| 상황 | 권장 방식 | 이유 |
|:---|:---|:---|
| 보고서, 회의록, 가이드처럼 본문 중심 문서를 반복 작성하고 양식을 지켜야 함 | 하이브리드 | 내용과 서식이 분리되어 문서마다 소스가 짧고, 서식은 한 번만 관리 |
| 서식 요구가 단순한 일회성 문서 | 마크다운 + pandoc | 템플릿 비용을 들일 이유가 없음 |
| 셀 병합, 복잡한 표, 섹션별 다른 여백, 조건부 서식 | docx-js | 템플릿이 표현하지 못하는 레이아웃을 코드로 제어 |
| 데이터로 문서 수백 건을 자동 생성 | docx-js | 반복문과 데이터 바인딩이 자연스러움 |
| 이미 있는 docx를 고쳐야 함 | XML 직접 편집 | 세 방식 모두 새 문서 생성 도구 |

실제로는 이 표를 위에서 아래로 훑기보다 다음 순서로 자문하는 편이 빠릅니다. 먼저 이미 있는 파일을 고치는 일인지 묻고, 그렇다면 XML 편집으로 갑니다. 아니라면 데이터로 대량 생성하거나 템플릿으로 표현할 수 없는 레이아웃이 필요한지 묻고, 그렇다면 docx-js입니다. 둘 다 아니라면 본문 중심 문서이므로 하이브리드로 시작하되, 서식 요구가 정말 단순하고 한 번뿐이라면 템플릿 없이 pandoc 기본 스타일로 충분합니다. 이 질문들은 결국 2장의 질문, 곧 서식을 누가 어디서 결정하게 할 것인가에 대한 답을 구하는 과정입니다.

한 가지 짚어 둘 점이 있습니다. 세 방식은 배타적이지 않습니다. 하이브리드로 만든 문서에서 표 하나만 셀 병합이 필요하다면 그 문서만 python-docx로 후처리하거나, 그 부분만 docx-js로 만든 조각을 합치는 식으로 섞어 쓸 수 있습니다. 기본은 하이브리드로 두고 필요한 부분만 정밀 도구로 보완하는 것이 현실적입니다.

# 7. 하이브리드 구현 절차

## 7.1 pandoc은 스타일 이름으로 서식을 찾습니다

하이브리드에서 가장 중요한 규칙은 pandoc이 스타일을 ID가 아니라 이름(`w:name`)으로 찾는다는 점입니다. 템플릿의 스타일 이름이 pandoc이 기대하는 이름과 일치해야 서식이 적용되고, 일치하지 않으면 기본값으로 처리됩니다. 이번 실험에서 사용한 대응은 다음과 같습니다.

| 마크다운 요소                       | 스타일 이름                     |
|:------------------------------------|:--------------------------------|
| 문서 제목, 부제, 날짜 (YAML 머리글) | Title, Subtitle, Date           |
| `#`, `##`, `###` 제목               | Heading 1, Heading 2, Heading 3 |
| 제목 바로 다음 문단                 | First Paragraph                 |
| 일반 문단                           | Body Text                       |
| 목록 항목, 표 셀 안의 문단          | Compact                         |
| 인용문 (`>`)                        | Block Text                      |
| 코드 블록                           | Source Code                     |
| 인라인 코드                         | Verbatim Char (문자 스타일)     |
| 표                                  | Table (표 스타일)               |
| 링크                                | Hyperlink (문자 스타일)         |

이 문서의 인용 상자, 코드 블록, 표는 모두 이 대응을 통해 템플릿의 스타일이 적용된 것입니다.

## 7.2 템플릿 만들기

템플릿은 앞의 스타일 이름에 맞춰 정의만 해 두면 됩니다. docx-js로 만들 때는 스타일마다 `id`와 함께 `name`을 pandoc이 기대하는 이름으로 지정합니다.

    {
      id: "Heading1", name: "Heading 1",
      basedOn: "Normal", next: "BodyText", quickFormat: true,
      run: { size: 32, bold: true, color: "1F3864" },
      paragraph: { spacing: { before: 360, after: 120 }, keepNext: true, outlineLevel: 0 },
    }

표 스타일은 docx-js에 전용 API가 없으므로 XML을 문자열로 만들어 `importedStyles`에 넣습니다. 이때 `fromXmlString`이 돌려주는 값은 문서 루트를 감싼 래퍼이므로 `root[0]`으로 실제 스타일 요소를 꺼내야 하고, 그렇지 않으면 스타일 파일에 `undefined`라는 요소가 끼어들어 검증에 실패합니다.

    const fromStyleXml = (xml) => ImportedXmlComponent.fromXmlString(xml).root[0];
    const tableStyle = fromStyleXml(`<w:style ${W} w:type="table" w:styleId="Table">...</w:style>`);
    new Document({ styles: { paragraphStyles: [...], importedStyles: [normalStyle, tableStyle] }, ... });

쪽 번호는 템플릿 구역에 바닥글을 넣어 두면 됩니다. pandoc은 템플릿의 페이지 설정과 머리글, 바닥글을 그대로 가져오므로, 이 문서 하단의 쪽 번호도 템플릿에서 온 것입니다.

## 7.3 마크다운 작성과 변환

마크다운 쪽에서 신경 쓸 것은 표입니다. 숫자 열을 오른쪽 정렬하려면 구분선에 콜론을 붙이고(`---:`), 열 너비를 정하려면 구분선의 대시 개수로 비율을 표현합니다. 다만 대시 비율은 표의 어떤 행이 `--columns` 폭을 넘을 때만 적용되므로, 짧은 표에서도 비율을 쓰고 싶다면 `--columns=30`처럼 작은 값을 줍니다. 변환과 확인은 다음 순서로 합니다.

    pandoc report.md --columns=30 --no-highlight --reference-doc=template.docx -o report.docx
    soffice --headless --convert-to pdf report.docx
    pdftoppm -jpeg -r 80 report.pdf page

마지막 두 줄은 만든 문서를 PDF와 이미지로 렌더링해 눈으로 확인하는 단계입니다. 변환이 성공했다는 것과 문서가 의도대로 보인다는 것은 다른 이야기이므로 이 단계를 건너뛰지 않는 것이 좋습니다.

# 8. 유의할 점과 흔한 오해

## 8.1 흔한 오해 네 가지

첫 번째 오해는 “pandoc은 서식을 제어할 수 없다”는 생각입니다. 마크다운 본문만 보면 그렇게 느껴지지만, 서식은 템플릿에서 제어하므로 스타일, 표 모양, 페이지 설정, 쪽 번호까지 정할 수 있습니다. 못하는 것은 본문 안에서 개별 요소의 서식을 하나하나 바꾸는 일입니다.

두 번째는 “토큰이 적게 드니 항상 이득”이라는 생각입니다. 이번 실험의 1,445토큰은 완성된 템플릿 스크립트의 크기일 뿐이고, 그것을 만드는 과정에서 있었던 시행착오는 들어 있지 않습니다. 실제로 `undefined` 래퍼 문제와 글꼴 기본값이 출력되지 않는 문제를 만나 여러 번 고쳤습니다. 템플릿은 작게 시작해 필요한 스타일만 늘려 가는 편이 안전합니다.

세 번째는 “템플릿은 docx-js로만 만들 수 있다”는 생각입니다. 템플릿은 어떤 도구로 만들어도 결국 스타일이 정의된 docx 파일이고, Word에서 스타일을 편집해 저장한 파일도 똑같이 `--reference-doc`으로 쓸 수 있습니다. docx-js는 코드로 관리하고 싶을 때의 한 가지 선택지입니다.

네 번째는 “변환이 성공하면 문서가 정상”이라는 생각입니다. 이번 실험에서 pandoc이 만든 파일은 docx 명세 검증기(XSD)를 통과하지 못했습니다. 오류는 pandoc이 만든 번호 매기기, 설정, 본문 XML의 일부 요소 순서 등에서 났고 기본 스타일로 변환한 파일도 똑같았으며, 템플릿의 스타일 파일은 검증을 통과했습니다. pandoc 결과물은 흔히 Word에서 열리지만, 이번 세션에서는 Word로 직접 열어 확인하지 못했습니다. 중요한 문서라면 Word에서 열어 보는 단계를 넣으세요.

## 8.2 docx-js를 쓸 때의 함정

docx-js는 기본값이 직관과 다른 곳이 몇 군데 있습니다. 용지 크기는 기본이 A4이므로 미국 Letter가 필요하면 명시해야 하고, 표는 `columnWidths`와 각 셀의 `width`를 둘 다 DXA 단위로 지정해야 합니다. 표 음영에는 `ShadingType.SOLID`가 아니라 `CLEAR`를 써야 검게 칠해지지 않습니다. 글머리 기호는 문자 `•`를 직접 넣지 말고 번호 매기기 설정을 사용해야 하고, 줄바꿈은 `\n`이 아니라 별도의 `Paragraph`로 나눕니다. 쪽 나누기는 반드시 `Paragraph` 안에 넣어야 하고, 이미지에는 `type`이 필수입니다. 이 사례들은 하나의 원칙으로 묶입니다. docx-js는 명세의 구조를 그대로 노출하므로, docx가 요구하는 구조를 어기면 조용히 잘못된 문서가 나옵니다.

> **유의.** docx-js로 템플릿을 만들 때는 글꼴과 기본 크기를 `default` 옵션이 아니라 `Normal` 스타일에 직접 지정하세요. 이번 환경에서는 `default` 옵션의 글꼴이 파일에 기록되지 않았습니다.

## 8.3 pandoc과 하이브리드를 쓸 때의 함정

스타일 이름 일치가 가장 흔한 실수 지점이고, 그다음이 표 열 너비입니다. 대시 비율이 적용되는 조건은 앞서 설명했고, 그래도 원하는 절대 너비를 정확히 맞추기는 어렵습니다. 이번 실험에서도 44 대 28 대 28을 목표로 했지만 46 대 27 대 27이 나왔습니다. 목차는 `--toc`로 넣을 수 있지만 필드 형태라서 Word에서 열 때 갱신해야 채워집니다. 글꼴은 템플릿에 지정한 서체가 열람하는 컴퓨터에 없으면 다른 서체로 대체되므로, 한글 문서는 `eastAsia` 글꼴까지 지정하고 배포 대상 환경의 글꼴을 확인해야 합니다.

마지막으로, 템플릿은 이 작업 환경에서 세션 사이에 자동으로 보존되지 않습니다. 템플릿 파일은 별도로 보관해 두고, 다음에 문서를 만들 때 다시 첨부해야 같은 서식을 얻습니다.

## 8.4 확인하지 못한 것

이번 실험은 작은 문서 한 건만 다뤘으므로 다음은 검증하지 못했습니다. Word에서의 실제 표시, 긴 문서에서의 토큰 절감 폭, 이미지와 각주와 수식과 목차의 실제 동작, 템플릿에서 목록 모양을 바꾸는 방법, 회사에서 이미 쓰는 Word 양식 파일을 그대로 `--reference-doc`으로 쓸 때 pandoc이 기대하는 스타일이 모두 들어 있는지 여부입니다. 이런 요구가 있다면 본격적으로 쓰기 전에 짧은 샘플로 먼저 시험해 보길 권합니다.

# 9. 마무리

이 문서의 핵심은 docx가 내용과 서식이 분리된 구조라는 사실이고, 세 방식은 그 분리를 어디에서 다루느냐가 다를 뿐입니다. docx-js는 분리를 코드 안에서 다루어 통제력을 얻는 대신 작성량을 치르고, 마크다운 + pandoc은 서식을 기본값에 맡겨 작성량을 최소화하는 대신 서식을 포기하며, 하이브리드는 서식을 템플릿이라는 별도 파일로 옮겨 둘 사이를 절충합니다. 본문 중심 문서라면 하이브리드가 대부분의 경우 최선이고, 실험에서 문서 두 건째부터 이득이 나기 시작했습니다.

다음 단계로는 세 가지를 권합니다. 자주 만드는 문서 양식이 있다면 그 양식에 맞춰 템플릿을 만들어 두고, 새 문서를 만들 때 짧은 샘플을 먼저 변환해 서식을 확인하며, 정밀 제어가 필요한 예외적인 부분만 python-docx나 docx-js로 보완하세요.
